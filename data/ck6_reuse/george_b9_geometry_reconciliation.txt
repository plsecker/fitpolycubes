6. CORPUS MEMBERSHIP AND THE V45 DISCREPANCY (forensic chain)
-----------------------------------------------------------------------
The reconstructed target is an exact-CK6, connected, 45-cell target
containing the centre cell, max L1 = 5 << universe radius 22. Under the
corpus conventions (after the proper rotation
diag(1,-1,0,-1) aligning its CK6 subgroup onto the corpus subgroup) it

Forensic results, each through the driver's own code:
  a) funnel_and_cover(build_universe(45) ball universe, piece M):
     SAT, 12 covers, counters {'pass coverage': 1, 'TILEABLE': 1}.
     -> funnel/placement/exact-cover machinery is sound here.
  b) placement audit: PlacementIndex 140 rows, coverage complete;
     exhaustive min-corner enumeration 134 unique placements;
     0 placements have an anchor outside the ball
     -> no ball-domain anchor incompleteness for this target.
  c) enumeration reachability: exact bounded BFS replay of the
     iter_targets_seeded mechanics over the target's own orbits:
     target mask REACHABLE (6,976 states)
     -> iter_targets_seeded(un, 3590, 22) would enumerate it.

  d) BUT: data/ck6_v45/shards.json contains only 86 min-ids, range
     [3652..3937]. Min-id 3590 has NO SHARD.
     data/ck6_v45/minid_counts.json hist has NO entry below 3652.

ROOT CAUSE: the sharded count pass (t_ck6_oddity_v35_search.py,
cmd_count) pre-filters candidate min-ids by "seeded reachability":
an orbit id s is admitted only if reachable from some START-FRONT
orbit s0 through a chain of adjacent orbits with ids >= s0
(id-nondecreasing FROM THE ROOT). That criterion is unsound. George's
target is the counterexample: its minimum orbit 3590 lies BELOW its
own centre-adjacent orbits (3652, 3937), so no non-decreasing chain
from either start orbit reaches it, yet a perfectly valid seeded DFS
from orbit 3590 grows the target (verified). The count pass therefore
recorded zero targets for min-id 3590 (and everything else below
3652), the plan built no shard for it, and the target was never
enumerated, never funneled, never covered.

The corpus totals are internally self-consistent (count pass and run
pass use the same prefiltered partition; 1,469,999 == expected), which
is why the incompleteness was invisible to the Stage validation.
